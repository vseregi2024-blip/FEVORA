# FEVORA IMPERIA — отчёт этапа F2

**Этап:** правила и архитектура начисления бонусов за процедуры
**Дата проверки:** 11.09.2026
**Режим:** архитектурный аудит и проектирование без реальных начислений

## 1. Итог этапа

Правило будущей интеграции определено однозначно:

- бонусное событие разрешено только для существующей, не удалённой процедуры со статусом `COMPLETED`;
- клиент должен быть заранее связан с Beauty Bonus Club через `CosmetologyClient.loyaltyClientId`;
- процедура должна быть полностью оплачена: `paidAmount = paymentAmount`;
- сумма будущего события — фактически оплаченная сумма `paidAmount`, а не плановая цена, себестоимость или прибыль;
- FEVORA не рассчитывает бонус и не хранит баланс, уровень или историю бонусов;
- Bot Client остаётся единственным источником истины и сам применяет актуальные процент, уровень и referral rules;
- одна процедура должна формировать не более одного финального события с постоянным ID `fevora:appointment:<visitId>:final`.

На F2 отправка события не реализована. POST API, начисления, списания, webhook и изменения Bot Client не создавались.

## 2. Что реально существует в FEVORA

### Состояния процедуры

В `CosmetologyVisitStatus` реально существуют:

| Статус | Фактическое значение |
|---|---|
| `SCHEDULED` | Активная запись, процедура ещё не закрыта |
| `COMPLETED` | Процедура закрыта, материалы списаны, финальная стоимость зафиксирована |
| `CANCELLED` | Запись отменена/мягко удалена |
| `NO_SHOW` | Клиент не пришёл; статус предусмотрен схемой |

Отдельных статусов «проведена» и «закрыта» нет: сейчас они объединены в `COMPLETED`.

### Поля процедуры, пригодные для будущей интеграции

| Данные | Существующее поле | Вывод |
|---|---|---|
| ID записи | `CosmetologyVisit.id` | Использовать в external event ID |
| Клиент FEVORA | `CosmetologyVisit.clientId` | Внутренняя связь |
| Клиент Bot Client | `CosmetologyClient.loyaltyClientId` | Единственный внешний идентификатор клиента |
| Дата процедуры | `CosmetologyVisit.operationDate` | Можно передавать как дату процедуры |
| Статус | `CosmetologyVisit.status` | Требовать `COMPLETED` |
| Плановая сумма | `CosmetologyVisit.plannedAmount` | Не использовать как базу бонуса |
| Финальная стоимость | `CosmetologyVisit.paymentAmount` | Контроль ожидаемой итоговой оплаты |
| Фактически получено | `CosmetologyVisit.paidAmount` | База будущего события после полной оплаты |
| Себестоимость | `CosmetologyVisit.costAmount` | Не передавать для расчёта бонуса |
| Прибыль | `CosmetologyVisit.profitAmount` | Не передавать для расчёта бонуса |
| Услуги | `CosmetologyVisitService[]` | Передавать детализацию одним массивом |
| Название услуги | `CosmetologyVisitService.name` | Детализация |
| Цена услуги | `CosmetologyVisitService.price` | Детализация, не самостоятельное bonus event |
| Платёжные движения | `CosmetologyWalletMovement[]` | Содержат предоплату/доплату и кошельки |
| Валюта | `Transaction.currency` | По умолчанию `UAH`; у самой процедуры поля валюты нет |

### Состояния оплаты

Отдельного поля `paymentStatus` сейчас нет. На F2 состояние можно описать только как производное:

| Производное состояние | Условие | Бонусное событие |
|---|---|---|
| `UNPAID` | `SCHEDULED`, `paidAmount = 0` | Нет |
| `PREPAID` | `SCHEDULED`, `paidAmount > 0` | Нет |
| `COMPLETED_UNPAID` | `COMPLETED`, `paidAmount = 0`, `paymentAmount > 0` | Нет |
| `COMPLETED_PARTIALLY_PAID` | `COMPLETED`, `0 < paidAmount < paymentAmount` | Нет |
| `PAID` | `COMPLETED`, `paidAmount = paymentAmount`, сумма больше нуля | Событие готово к будущей отправке |
| `INVALID_OVERPAYMENT` | `paidAmount > paymentAmount` | Запрещено; текущая логика закрытия уже блокирует переплату |
| `CANCELLED/NO_SHOW` | соответствующий статус | Нет |

Критический факт: `COMPLETED` сам по себе не означает `PAID`. Текущий код позволяет закрыть процедуру с долгом, а экран «Мне должны» находит записи, где `paymentAmount > paidAmount`.

## 3. Бизнес-правила F2

### Новая запись

Создание записи устанавливает `status = SCHEDULED` и `paymentAmount = 0`. В Bot Client ничего не отправляется. Бонус равен нулю.

### Предоплата

Предоплата записывается как реальные финансовые операции FEVORA типа `PREPAYMENT` и увеличивает `paidAmount`, но не создаёт бонусное событие. До закрытия и полной оплаты процедуры начисление запрещено.

### Проведение и закрытие процедуры

При закрытии FEVORA:

- фиксирует финальную сумму в `paymentAmount`;
- добавляет полученную доплату к `paidAmount`;
- списывает материалы;
- рассчитывает `costAmount` и `profitAmount`;
- переводит запись в `COMPLETED`.

Будущее событие разрешается только после дополнительной проверки полной оплаты. Само закрытие без полной оплаты события не создаёт.

### Предоплата плюс доплата

Предоплата 1 000 грн и доплата 4 000 грн при финальной цене 5 000 грн должны дать одно событие:

```text
external_event_id = fevora:appointment:<visitId>:final
amount = 5000.00
```

Отдельные события на 1 000 и 4 000 создавать нельзя. `incomeTransactionId` нельзя использовать как идентификатор loyalty event: он указывает только на первую финансовую транзакцию записи, а оплат может быть несколько.

### Несколько услуг

`CosmetologyVisitService[]` уже поддерживает несколько услуг в одной записи. Независимо от количества услуг формируется одно итоговое событие на запись. Услуги передаются только как детализация.

### Скидка

База бонуса — фактически полученная сумма. Для цены услуг 5 000 грн, скидки 500 грн и оплаты 4 500 грн событие должно содержать `amount = 4500.00`.

Отдельного поля `discountAmount` сейчас нет. После закрытия `plannedAmount` перезаписывается финальной суммой, однако цены отдельных `CosmetologyVisitService` сохраняются. Явную скидку FEVORA сейчас не хранит как самостоятельный факт. Для F2 это не мешает правилу «использовать фактическую оплату», но для будущего аудита скидок потребуется отдельное решение.

### Себестоимость и прибыль

`costAmount`, `profitAmount`, складские партии и списания материалов не входят в базу начисления и не должны передаваться Bot Client для расчёта бонуса.

### Клиент без связи

Если `loyaltyClientId = null`, событие не создаётся и интерфейс должен показывать: **«Клиент не подключён к программе лояльности»**.

После подключения идентификация выполняется только по `loyaltyClientId`. Повторный поиск по телефону или имени при оплате запрещён.

### Отвязка клиента

Отвязка не меняет историю процедур и не удаляет ранее отправленные события. Неотправленную процедуру без актуального `loyaltyClientId` автоматически отправлять нельзя.

### Отмена, возврат и оплата бонусами

- `CANCELLED` и `NO_SHOW` не создают событие.
- Возврат на F2 не реализуется; отрицательный payment запрещён.
- Если событие уже было отправлено, последующая отмена потребует отдельного reversal API.
- Оплата бонусами на F2 не реализуется; правила не определяются и бонусы не списываются.

## 4. Идемпотентность и retry

Предлагаемый стабильный идентификатор:

```text
fevora:appointment:<CosmetologyVisit.id>:final
```

Он детерминирован, не меняется при retry и не зависит от локального `Transaction.id`.

Надёжная защита от дубля требует двух сторон:

1. FEVORA хранит один delivery record на одну процедуру и использует уникальный `externalEventId`.
2. Bot Client принимает `external_event_id` и гарантирует уникальность на уровне БД/API.

Без уникальности в Bot Client гарантировать отсутствие двойного начисления при сетевом сбое невозможно: FEVORA может не получить ответ после фактической обработки запроса.

Минимальные состояния доставки:

- `NOT_SENT` — готово, но ещё не отправлялось;
- `SENDING` — попытка выполняется;
- `SENT` — Bot Client подтвердил приём;
- `FAILED` — безопасная повторная отправка тем же external event ID разрешена.

Retry обязан повторять тот же payload и тот же `external_event_id`. Новый случайный ID запрещён. Зависшее `SENDING` должно возвращаться в retry только по контролируемому timeout/lease, а не создавать новую сущность.

## 5. Предлагаемый payload будущего API

Это контракт для следующего этапа, не реализованный на F2:

```json
{
  "external_event_id": "fevora:appointment:<visitId>:final",
  "client_id": "<loyaltyClientId>",
  "appointment_id": "<visitId>",
  "amount": "5000.00",
  "currency": "UAH",
  "date": "2026-09-11",
  "services": [
    {
      "id": "<visitServiceId>",
      "name": "Ботокс",
      "amount": "2000.00"
    }
  ]
}
```

Не передавать как базу расчёта: `plannedAmount`, `costAmount`, `profitAmount`, локальный процент, локальный уровень или локальный bonus balance.

Ожидаемый будущий ответ Bot Client:

- `accepted`;
- `external_event_id`;
- удалённый payment ID;
- фактически начисленные бонусы;
- актуальный bonus balance.

FEVORA не должна делать из возвращённого баланса локальный источник истины; актуальный профиль продолжает читаться из Bot Client.

## 6. Нужна ли отдельная структура БД

Для реальной отправки и безопасного retry отдельная минимальная структура нужна, но на F2 она **не создана**.

Рекомендуемая будущая таблица `CosmetologyLoyaltyDelivery`:

| Поле | Назначение |
|---|---|
| `id` | Внутренний ID |
| `visitId` unique | Строго одна финальная доставка на процедуру |
| `loyaltyClientId` | Снимок адресата на момент подготовки |
| `externalEventId` unique | Идемпотентность |
| `amount` | Зафиксированная фактическая сумма события |
| `currency` | Валюта события |
| `status` | `NOT_SENT/SENDING/SENT/FAILED` |
| `attemptCount` | Количество попыток |
| `lastAttemptAt` | Последняя попытка |
| `sentAt` | Подтверждённая отправка |
| `remotePaymentId` | ID принятого payment в Bot Client |
| `lastErrorCode` | Безопасный технический код без secret и персональных данных |
| `createdAt/updatedAt` | Аудит |

Не добавлять в эту таблицу `bonus_balance`, `bonus_transactions`, `level_name` или `level_bonus_percent`.

Delivery record должен создаваться транзакционно только при переходе записи в состояние полной оплаты. Сетевой запрос нельзя выполнять внутри финансовой DB-транзакции: сначала фиксируется локальное состояние, затем отдельный worker/server action отправляет событие.

## 8. Обнаруженные пробелы перед следующим этапом

1. Нет POST payment endpoint в Bot Client и серверного POST-клиента в FEVORA.
2. Нет уникальности `external_event_id` на стороне Bot Client.
3. Нет локального delivery/outbox состояния и интерфейса `NOT_SENT/SENDING/SENT/FAILED`.
4. Нет отдельного `paymentStatus`; полная оплата определяется сравнением сумм.
5. Тип `DEBT_PAYMENT` существует, но пользовательский сценарий доплаты уже закрытой процедуры в текущем коде не найден. Пока долг нельзя штатно довести до полной оплаты и затем подготовить событие.
6. У процедуры нет собственного поля валюты. Текущие финансовые транзакции используют `UAH` по умолчанию; будущий контракт должен зафиксировать источник валюты.
7. Нет отдельного поля скидки; явная история скидки не сохраняется.
8. Возврат/reversal и оплата бонусами не спроектированы на уровне API — согласно заданию оставлены будущими этапами.
9. Нулевая процедура не должна формировать payment event до отдельного решения Bot Client; бонус в любом случае равен нулю.

## 9. Что потребуется для следующего этапа

Перед включением реальных начислений необходимо отдельное разрешение и согласованный контракт обеих систем:

1. Реализовать в Bot Client идемпотентный POST payment с уникальным `external_event_id`.
2. Сначала протестировать endpoint на тестовой БД/клиенте, включая потерянный ответ и повторный запрос.
3. Добавить в FEVORA минимальную delivery/outbox структуру отдельной migration.
4. Реализовать чистую функцию eligibility и формирование неизменяемого payload.
5. Реализовать доплату долга, после которой запись впервые становится полностью оплаченной.
6. Добавить серверную отправку с timeout, безопасными ошибками и retry тем же event ID.
7. Добавить в карточку процедуры статусы передачи и ручную кнопку «Повторить» только для `FAILED`.
8. Провести production smoke test на одном явно разрешённом тестовом платеже и проверить отсутствие изменений в `MoneyAccount`, `Envelope` и общем капитале.

## 10. Что не реализовано на F2

- реальный POST payment;
- начисление или списание бонусов;
- изменение bonus balance, bonus transactions, payments или referrals;
- изменение Bot Client;
