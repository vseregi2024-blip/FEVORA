# FEVORA — Master Technical Specification

## 0. Статус документа

Название проекта: FEVORA
Тип документа: Master Technical Specification / основное техническое задание
Версия: 1.0
Дата: 11 августа 2026
Статус: базовая спецификация для старта разработки в Codex.

Этот документ является главным источником требований для первой версии FEVORA. Если в процессе разработки возникает противоречие между предположением разработчика и данным документом, приоритет имеет этот документ. Codex не должен самостоятельно расширять продукт новыми модулями, сложной аналитикой или интеграциями, которые здесь не предусмотрены.

## 1. Что такое FEVORA

FEVORA — простая личная система учета денег и хозяйственных направлений, работающая как понятный «личный бухгалтер», а не как сложная ERP и не как AI-продукт.

Основная задача: пользователь быстро фиксирует денежные операции и ключевые хозяйственные данные, а система показывает понятный остаток, расходы, обязательства и состояние отдельных направлений.

FEVORA должна быть удобной для ежедневного использования с телефона и компьютера. Ввод данных должен занимать минимум действий.

Первый релиз строится вокруг:
1) общего финансового ядра;
2) раздела «Семья»;
3) раздела «Птицеводство»;
4) Telegram-бота для быстрого ввода.

Модули «Косметология», «Инфобизнес/обучение», «Товары» и другие направления не реализуются в первом релизе, но архитектура должна позволять подключить их позже без переписывания финансового ядра.

## 2. Главные продуктовые принципы

1. Простота важнее количества функций.
2. Любую обычную операцию пользователь должен иметь возможность внести за 10–20 секунд.
3. FEVORA не должна требовать банковской интеграции.
4. FEVORA не должна быть AI-системой в MVP.
5. Основной способ учета — ручной ввод через приложение или быстрый ввод через Telegram.
6. Система не должна заставлять пользователя вести данные, которые он фактически не измеряет. Например, не требовать ежедневного взвешивания корма или птицы.
7. Денежные операции хранятся в едином финансовом ядре, а модули добавляют к ним свой контекст.
8. Все суммы и расчеты должны быть прозрачны: пользователь должен понимать, откуда взялась цифра.
9. Никаких автоматических списаний, банковских подключений и скрытых изменений данных.
10. Сначала стабильный MVP, затем расширение.

## 3. Объем первого релиза (MVP)

В MVP входят:

— Авторизация владельца.
— Главный экран.
— Единый журнал денежных операций.
— Доходы.
— Расходы.
— Обязательные ежемесячные платежи.
— Накопления/сбережения.
— Текущий расчетный баланс.
— Категории.
— Раздел «Семья».
— Раздел «Птицеводство».
— Telegram-бот: текст, голос, фото/чек и ручное уточнение.
— Базовая статистика по периодам.
— Поиск и фильтры.
— Редактирование и удаление записей.
— Резервное хранение данных в PostgreSQL.
— Адаптивная браузерная версия, удобная на телефоне и компьютере.
— Возможность установить веб-приложение как PWA, если это не усложняет архитектуру.

Не входят в MVP:

— банковская синхронизация;
— открытый банкинг;
— AI-помощник;
— автоматическая бухгалтерская отчетность для налоговых органов;
— полноценная CRM;
— календарь записи клиентов;
— косметология;
— инфобизнес;
— склад товаров;
— нативные отдельные приложения iOS/Android;
— сложная многопользовательская корпоративная система.

## 4. Роли и доступ

На первом этапе достаточно одной основной роли: Owner / Владелец.

Владелец:
— видит все модули;
— создает, редактирует и удаляет операции;
— управляет категориями;
— настраивает обязательные платежи;
— подключает Telegram;
— просматривает статистику и баланс.

Архитектура БД должна позволять позже добавить членов семьи или сотрудников с ограниченными правами, но UI управления ролями в MVP не нужен.

## 5. Рекомендуемая техническая архитектура

Рекомендуемый стек для MVP:

Frontend + web application: Next.js + TypeScript.
UI: React, адаптивный интерфейс, mobile-first.
Backend: серверная часть Next.js или отдельный API-слой внутри того же репозитория.
Database: PostgreSQL.
ORM: Prisma.
Deployment: Railway.
Domain: собственный домен FEVORA.
Telegram: официальный Telegram Bot API.
Files/photos: объектное хранилище, совместимое с S3, либо подходящее файловое хранилище в выбранной инфраструктуре.
Authentication: безопасная авторизация по email/паролю или magic link; конкретную реализацию Codex выбирает из поддерживаемых решений без привязки к нестабильной версии библиотеки.
Validation: серверная валидация всех финансовых операций.
Logging: базовый журнал ошибок, без записи секретов.

Репозиторий должен быть единым и понятным. Не создавать микросервисную архитектуру для MVP.

## 6. Структура интерфейса

Основная навигация:

1. Главная
2. Проекты
3. Добавить
4. Отчёты
5. Настройки

Старая навигация «Главная / Финансы / Семья / Птицеводство / Настройки» устарела. Проекты открываются через раздел «Проекты»; активны «Семья» и «Птицеводство».

На мобильном — нижняя навигация или компактное меню.
На компьютере — боковое меню.

### Единая дизайн-система

Интерфейс mobile-first рассчитан прежде всего на ширину 360–430 px: тёплый светлый фон, спокойные белые карточки, графитовый текст, sage green для доходов и terracotta для расходов. Ключевые суммы визуально доминируют, а основные действия имеют touch target не менее 44 px.

Общие компоненты включают карточки, статусы, заголовки разделов, empty states, line icons, кнопки, формы и нижнюю навигацию. Центральная кнопка «Добавить» выделена визуально. На desktop сохраняется тот же интерфейс с ограниченной шириной контента и боковой навигацией.

Все пять направлений отображаются в проектах: активны «Семья», «Птицеводство» и «Товарка»; «Косметология» и «Инфобизнес» показываются как «Скоро».

Ключевая кнопка на всех основных экранах: «+ Добавить».

Главный экран должен отвечать на вопрос «Что у меня сейчас с деньгами?» и показывать:
— текущий баланс;
— доходы за выбранный период;
— расходы за выбранный период;
— обязательные платежи, которые ожидаются;
— быстрые кнопки добавления;
— краткий итог по Семье;
— краткий итог по Птицеводству.

Не перегружать главный экран графиками.

## 7. Единое финансовое ядро

Все денежные записи должны храниться в общей сущности Transaction.

Базовые типы:
— income — доход;
— expense — расход;
— saving_in — перевод в накопления;
— saving_out — возврат из накоплений;
— adjustment — ручная корректировка баланса при необходимости.

Каждая операция содержит минимум:
— id;
— owner_id;
— type;
— amount;
— currency;
— operation_date;
— category_id;
— module: general / family / poultry / goods;
— description/комментарий;
— source: web / telegram;
— created_at;
— updated_at.

Дополнительно:
— attachment/photo;
— связанная сущность модуля;
— признак обязательного платежа;
— теги при необходимости.

Сумма не должна храниться как float. Использовать безопасный денежный тип/decimal.

## 8. Баланс и расчеты

Базовая формула текущего расчетного баланса:

Баланс = стартовый остаток + доходы − расходы − переводы в накопления + возвраты из накоплений ± корректировки.

Накопления отображаются отдельно и не должны ошибочно считаться обычным расходом «потерянных денег».

Пользователь может выбрать период:
— сегодня;
— неделя;
— месяц;
— произвольный диапазон.

Система обязана пересчитывать итоги после создания, изменения или удаления операции.

Все расчеты выполняются на сервере или проверяются сервером. Нельзя доверять только цифре, посчитанной в браузере.

## 9. Обязательные ежемесячные платежи

Отдельная сущность RecurringPayment / «Обязательный платеж».

Примеры: рассрочка, коммунальные услуги, кредит, регулярная оплата сервиса и другие заранее известные платежи.

Поля:
— название;
— сумма;
— валюта;
— категория;
— день месяца или дата следующего платежа;
— модуль;
— активен/неактивен;
— комментарий;
— дата окончания, если известна.

Логика:
— обязательный платеж не должен автоматически становиться фактическим расходом без подтверждения;
— система показывает его как ожидаемый;
— пользователь нажимает «Оплачено»;
— после подтверждения создается обычная расходная операция;
— следующий платеж рассчитывается по заданной периодичности.

На главной показывать ближайшие обязательные платежи и общую сумму ожидаемых платежей.

## 10. Накопления

Раздел «Накопления» нужен для денег, которые пользователь сознательно откладывает.

Для MVP достаточно:
— создать цель/счет накоплений;
— внести сумму;
— вывести сумму;
— видеть текущий размер накоплений;
— видеть историю движения.

Поля цели:
— название;
— целевая сумма — необязательна;
— текущая сумма;
— комментарий;
— статус: active / completed / archived.

Накопления должны быть связаны с финансовым ядром, чтобы общий баланс не расходился.

## 11. Категории

Категории должны быть редактируемыми.

Системные стартовые категории для «Семьи»:
— дети;
— здоровье;
— развлечения;
— путешествия;
— рассрочки/обязательные платежи;
— продукты;
— дом;
— транспорт;
— другое.

Пользователь может:
— добавить категорию;
— переименовать;
— архивировать;
— выбрать иконку;
— изменить порядок.

Удалять категорию, к которой уже привязаны операции, физически нельзя. Ее нужно архивировать.

## 12. Модуль «Семья»

Цель модуля: простой контроль личных семейных доходов, расходов, накоплений и баланса без сложной бухгалтерии. Личные доходы Family не дублируют доходы бизнес-проектов.

Основной экран «Семья»:
— расходы семьи за период;
— личные доходы Family: продажа личных вещей, разовый доход и прочее;
— семейные накопления;
— обязательные семейные платежи;
— остаток/итог;
— распределение расходов по категориям;
— последние операции.

Действия:
— добавить расход;
— добавить личный доход Family;
— перевести в накопления;
— добавить обязательный платеж;
— открыть историю;
— отфильтровать по категории и периоду.

Не создавать отдельные сложные бюджеты на каждого члена семьи в MVP. Категории «дети», «здоровье» и т.п. достаточно.

Сбережения отображаются отдельно и не считаются доходом Family. Один чек может быть разбит на связанные расходные строки по нескольким категориям; общая сумма чека отдельной финансовой операцией не создаётся, поэтому не возникает двойного учёта.

## 13. Модуль «Птицеводство»

Цель модуля: единым действием зафиксировать хозяйственный факт, деньги и связанные показатели без двойного учета и без сложной ERP-логики.

Реализованы шесть разделов: финансы, поголовье по партиям, инкубация, корма и склад, продажи, операционные расходы. Все денежные записи используют общий `Transaction` с `module = POULTRY`.

Продажа создаёт ровно один доход Poultry и, если выбрана партия, одно движение поголовья. Изменение и soft delete продажи корректируют этот же доход и остаток партии. Оставлено семье и падеж уменьшают остаток без создания дохода.

Корма учитываются мешками: покупка создаёт один расход и одну складскую партию; назначение или завершение мешка уменьшает складской остаток, связывает корм с партией и не создаёт повторную денежную операцию.

Инкубация ведётся отдельными закладками с несколькими породами, неоплодом, потерями, вылуплением и процентом вывода. Партия из вылупившейся птицы создаётся только по явному подтверждению пользователя.

Стартовые категории расходов: Корма, Покупка птиці, Інкубаційні яйця, Ветеринарія / препарати, Обладнання і матеріали, Електрика / утримання, Проче. Категория дохода: Продаж продукції. Категории расширяемы.

Не требуется ежедневный учёт корма в килограммах или взвешивание птицы. Себестоимость партии показывает только однозначно связанные затраты: назначенные мешки и явно привязанные операционные расходы; общие расходы автоматически между партиями не распределяются.

## 14. Быстрый ввод через Telegram

Telegram-бот — один из главных способов ежедневного ввода.

Поддерживаемые сценарии MVP:

1. Текст.
Пример: «Корм 2 мешка 1000 грн птицеводство».
Бот не обязан применять AI. Для MVP допускаются:
— структурированные команды;
— кнопки;
— пошаговое уточнение полей;
— простой парсер известных шаблонов.

2. Голос.
Бот принимает голосовое сообщение. Если инфраструктура распознавания речи не подключена на первом спринте, бот должен сохранить голос как входящий черновик и предложить пользователю заполнить сумму/категорию кнопками. Распознавание речи может быть подключено как отдельный технический этап.

3. Фото/чек.
Фото прикрепляется к черновику или операции. OCR и автоматическое чтение чека не являются обязательными для MVP.

4. Ручной ввод кнопками.
Сценарий:
«Добавить» → «Расход/Доход» → «Семья/Птицеводство» → категория → сумма → комментарий → сохранить.

После сохранения бот показывает подтверждение:
тип, модуль, категория, сумма, дата.

Обязательно дать кнопки «Изменить» и «Удалить/Отменить» для последней созданной записи.

## 15. Черновики входящих данных

Для Telegram желательно иметь сущность InboxDraft.

Она нужна для голосовых сообщений, фото и неполных записей.

Статусы:
— new;
— needs_input;
— converted;
— discarded.

Черновик не влияет на баланс, пока не преобразован в подтвержденную финансовую операцию.

## 16. История, поиск и фильтры

Общий журнал операций должен поддерживать:
— поиск по тексту;
— период;
— тип операции;
— модуль;
— категорию;
— источник web/telegram;
— сортировку по дате.

Каждую запись можно открыть и увидеть:
— сумму;
— дату;
— категорию;
— модуль;
— комментарий;
— вложение;
— когда создана;
— откуда добавлена.

Редактирование должно вести к мгновенному корректному пересчету итогов.

## 17. Базовая статистика

В MVP статистика должна быть понятной, а не «финансовой аналитикой ради аналитики».

Нужно:
— доходы за период;
— расходы за период;
— чистая разница;
— расходы по категориям;
— расходы по модулям;
— динамика по месяцам;
— сумма обязательных платежей;
— размер накоплений.

Допустимы простые диаграммы, но цифры и списки важнее визуальных эффектов.

## 19. API и серверные правила

Основные группы серверных операций:

/auth
/transactions
/categories
/recurring-payments
/savings
/family
/poultry
/feed-purchases
/attachments
/telegram
/dashboard
/reports

Правила:
— все записи проверяются по user_id;
— пользователь никогда не может получить чужие данные;
— все финансовые изменения валидируются на сервере;
— удаление финансовых сущностей желательно soft-delete;

## 25.1. Актуальный интерфейс FEVORA

Интерфейс FEVORA построен mobile-first: на ширине 360–430 px используется нижняя навигация с выделенной центральной кнопкой «Добавить», а на широком экране — боковая навигация и ограниченная ширина контента.

Единая визуальная система использует тёплый светлый фон, белые карточки с мягкими границами, графитовый текст, sage green для положительных значений, terracotta для расходов и золотой акцент. Для интерфейса применяются единые line icons, карточки, статусы, пустые состояния, формы и диалог подтверждения удаления.

Навигация: Главная, Проекты, Добавить, Отчёты, Настройки. В проектах активны «Семья», «Птицеводство» и «Товарка»; «Косметология» и «Инфобизнес» обозначены как «Скоро».

Птицеводство разделено на короткие рабочие экраны: финансы, поголовье, инкубация, корма и склад, продажи и операционные расходы. ## 25.2. Товарка

При добавлении товара пользователь может сразу зафиксировать уже имеющийся стартовый остаток, его закупочную цену за единицу и дату внесения. Этот остаток создаёт FIFO-партию и влияет на себестоимость будущих продаж, но не создаёт повторный денежный расход. Для товара также можно задать цену продажи по умолчанию; она подставляется в новую продажу и может быть изменена в конкретной операции.

«Товарка» — отдельный модуль физического товара с категориями, товарами, закупками, FIFO-партиями, продажами, операционными расходами и инвентаризацией. Закупка создаёт один связанный денежный расход и партию склада; доставка может входить в себестоимость партии или стать отдельным операционным расходом. Продажа создаёт один связанный доход, уменьшает остаток и фиксирует FIFO-себестоимость и валовую прибыль без второго расхода денег. Списание и корректировка меняют только склад; списание сохраняет стоимость для аналитики. Продажу можно безопасно редактировать или мягко удалить с восстановлением остатков; использованную закупочную партию нельзя изменить или удалить. Отчёт «Товарка» показывает выручку, денежные расходы, COGS, валовую прибыль и прибыль по товарам. Все даты используют timezone `Europe/Kyiv` по умолчанию.

## 27.1. Модуль «Инфобизнес»

«Инфобизнес» — отдельный финансовый проект для образовательных продуктов: онлайн- и мини-курсов, вебинаров, офлайн-обучения, мастер-классов и индивидуального обучения. Он не является LMS, CRM студентов, рекламным кабинетом или системой автоматизации маркетинга.

Главная сущность — `InfoProduct`: название, свободно расширяемый тип продукта, формат (онлайн / офлайн / гибридный), базовая цена, даты, статус и комментарий. У продукта есть карточка с продажами, прямыми расходами, доходом и прибылью. Базовая цена подставляется в новую продажу, но пользователь всегда может изменить сумму.

`InfoSale` создаётся вместе с ровно одним `Transaction` типа `INCOME` и `module = INFOBUSINESS` в одной Prisma transaction. Продажа принадлежит продукту и может содержать покупателя/ученика, количество мест и комментарий. Редактирование обновляет тот же Income, а soft delete исключает одновременно продажу и Income из расчётов.

`InfoExpense` создаётся вместе с ровно одним `Transaction` типа `EXPENSE`. У расхода есть пользовательская `InfoExpenseCategory`, описание, дата, optional название сервиса и optional связь с `InfoProduct`. Стартовые категории создаются для пользователя при первом открытии модуля; собственные категории можно добавить, переименовать и архивировать. Архивирование не удаляет связанную историческую категорию и не ломает старые расходы.

Расход с `productId` уменьшает прибыль только этого продукта. Расход без `productId` считается общим расходом Инфобизнеса: он уменьшает общий результат, но никогда автоматически не распределяется и не вычитается из прибыли конкретного курса.

Формулы:

- прибыль продукта = доходы продукта − расходы продукта;
- общий результат Инфобизнеса = все доходы Инфобизнеса − все расходы Инфобизнеса, включая общие.

Аналитика поддерживает периоды сегодня / неделя / месяц / год, фильтры по продукту и категории, результаты продуктов, группировку расходов по категориям и сервисов по названию. Все операции проверяют владельца продукта и категории на сервере.
